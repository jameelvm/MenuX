## 3. Refinements made while applying the approved changes

These follow directly from the approved decisions. They are listed so nothing changes silently.

| # | Refinement | Follows from | Why it's necessary |
|---|-----------|--------------|--------------------|
| F1 | **No SQS in MVP-1.** All background work (publish jobs, manifest builds, QR/route projections, media processing, tenant purge) is a work item claimed with a lease (ADR-18). | P8 poller-only dispatch | The pollers already find all work, so a queue would add a second dispatch mechanism and more infrastructure without benefit at MVP volume. |
| F2 | **Per-location manifest serialization by a lease on `MANIFEST`** instead of an SQS FIFO queue; PUB-2 resolved by removal. | P8, PUB-2, PUB-5 | No FIFO means no dedup-ID defect, and the lease gives the same one-builder-per-location guarantee. |
| F3 | **No DynamoDB Streams in MVP-1.** Integration events from DynamoDB modules use transactional `OUTBOX` items (TI-4) dispatched by pollers. | P8, TI-4, TI-5 | Removes stream-consumer infrastructure; purge deletes can't trigger downstream writes through streams. TI-5 remains a rule for any future stream consumer. |
| F4 | **90 locations per menu** validation limit. | PUB-1, PUB-8, T7 | The commit transaction now has 7 fixed actions (guard, pointer, version, job, lock, outbox + headroom); DynamoDB allows 100 actions. |
| F5 | **Intentional upserts are explicit writer options** (`MANIFEST`, `TENANTGUARD`, counters); everything else uses `attribute_exists`. | TI-1 | Some state items are created on first use; the writer still guarantees tenant tags. |
| F6 | **GSI1 sort keys may contain normalized names truncated to 100 characters**; table keys may not contain user text. | TI-7 | The catalog's name-sorted GSI needs names. The key-character rule applies to table keys, which TENANT_SK copies. |
| F7 | **US defaults:** USD, `en-US`, FDA nine-allergen tag set, optional `calories` field on items/variants (pending L3), `us-east-1` region proposal. | C4 (US market) | Market-driven defaults needed for catalog design (week 3) and Terraform (week 9). The calorie field is optional and cheap, and avoids a later data-model change if L3 confirms the need. |

## 4. Final MVP-1 scope

Doc 12 §8 applies, with Rev 0.3 decisions:
- **MVP-1:** tenant registration + multiple locations (outlets = locations) · roles and permissions (BFF login, MFA for Owner/Admin) · food catalog, variants, modifiers, allergens (US tag set), multilingual content (default + up to 4) · menus, sections, placements, per-menu price overrides, schedules, sold-out flag via publish, locking · media uploads (WebP) · publishing (publish, rollback, unpublish) · QR codes (128-bit, PNG/SVG; PDF is flex) · static public menu · tenant export and deletion · static plan limits · first AWS environment with CI/CD, observability, restore drills.
- **Phase 2:** **AI menu import + Claude API integration (first phase-2 candidate)**, real-time sold-out overlay, AI translation, SaaS billing, analytics, branding/custom domains, location pricing, approval workflow, support console, automatic QR IP blocking, LeadingKeys policies, multi-account production, external pen test.
- **Future:** ordering, online payments, order board, integrations, organization hierarchy, retail inventory, customer accounts, customer-facing AI.

Flex scope and the protected tests: doc 10 §12.2–§12.3.
